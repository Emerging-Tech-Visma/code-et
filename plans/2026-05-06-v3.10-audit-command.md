# /code:audit — Local Mirror of the v3.9.0 CI Gate

**Date:** 2026-05-06
**Slug:** v3.10-audit-command
**Status:** Draft

## Problem Statement

In v3.9.0, code-et shipped a Rust Clean Architecture CI gate that runs seven stages of static analysis and tests on every PR. Today developers only see those failures after pushing — the round-trip (push → wait → fix → push) is slow and breaks flow during `/code:implement` runs. There is no local equivalent, and no way to invoke the gate ad-hoc on a working tree before a commit lands.

## Solution

Add `/code:audit`, a local command that runs the exact same seven-stage pipeline as the v3.9.0 CI gate against the current working tree: (1) `cargo fmt --all -- --check`, (2) `cargo clippy --workspace --all-targets --all-features -- -D warnings`, (3) layer-deps validator, (4) cargo-machete, (5) cargo-audit, (6) cargo-deny, (7) `cargo nextest run --workspace --all-features`. The CI workflow YAML remains the single source of truth for stage definitions; the audit command reads it and mirrors it stage-for-stage. A `--fast` mode (stages 1–2 only — fmt + clippy) plugs into `verify-gate.sh` so pre-commit feedback is sub-second on small diffs, and a `--review` mode chains the engineering plugin's `code-review` skill against the diff for human-readable findings.

## User Stories

1. US-1: As a developer working on a Rust crate, I want to run `/code:audit` and get the same pass/fail verdict CI will give me, so that I can catch gate failures before pushing.
2. US-2: As a developer mid-implementation, I want `/code:implement` to run a fast subset of the audit automatically after `simplify`, so that style and dead-code regressions surface inside the same loop.
3. US-3: As a developer running `verify-gate.sh`, I want stages 1–2 of the audit to run as part of the gate, so that pre-commit blocks regressions without adding seconds of latency.
4. US-4: As a developer debugging a single failing stage, I want `/code:audit --stage 3` to run only the dependency-hygiene checks, so that I can iterate without re-running the whole pipeline.
5. US-5: As a reviewer, I want `/code:audit --review` to chain the engineering plugin's code-review skill against the working diff, so that I get prose findings alongside the static-analysis output.
6. US-6: As a developer on a non-Rust repo, I want `/code:audit` to detect the absence of `Cargo.toml` and exit cleanly with a no-op message, so that the command is safe to wire into shared hooks.
7. US-7: As a developer reading audit output, I want a markdown report at `.claude/audit-<UTC>.md` with CRITICAL findings first and `path:line` citations on every finding, so that I can jump straight to the offending code.
8. US-8: As a maintainer of the v3.9.0 CI workflow, I want the audit command to parse stage definitions from the workflow YAML rather than duplicating them, so that local and CI never drift.
9. US-9: As a developer on a machine without `cargo-machete` / `cargo-audit` / `cargo-deny` installed, I want those stages to skip with a WARNING when the tool is missing, so that the command remains usable on a fresh dev machine.
10. US-10: As a developer using the bundled `templates/rust/dioxus-fullstack/` fixture, I want `/code:audit` to run cleanly against it as a smoke test, so that the fixture doubles as the audit's regression suite.
11. US-11: As Kennet using code-et across multiple repos (not just Visma projects), I want the audit command to contain zero hardcoded app names or org-specific paths, so that the plugin stays portable.
12. US-12: As a developer who just ran `/code:audit` and got a non-zero exit, I want the report to surface the single highest-severity finding at the top with a one-line remediation hint, so that I know exactly what to fix first.

## Acceptance Criteria

### US-1
- AC-1.1: Running `/code:audit` in a Rust workspace executes all seven stages from the v3.9.0 CI gate in order: (1) fmt (`cargo fmt --all -- --check`), (2) clippy with `-D warnings` (`cargo clippy --workspace --all-targets --all-features -- -D warnings`), (3) layer-deps validator (`bash scripts/layer-deps-validator.sh`), (4) cargo-machete, (5) cargo-audit, (6) cargo-deny, (7) tests (`cargo nextest run --workspace --all-features`).
- AC-1.2: Exit code is non-zero if any stage fails; the failing stage and command are named in the terminal output.
- AC-1.3: A clean working tree on the bundled fixture exits 0 with all seven stages reported as passed.

### US-2
- AC-2.1: The `implement` command's skill chain calls the audit skill with `--fast` immediately after `simplify`.
- AC-2.2: A `--fast` audit failure halts the implement loop with the audit report path surfaced in the chat.

### US-3
- AC-3.1: `verify-gate.sh` invokes the audit command in `--fast` mode when a `Cargo.toml` is detected at repo root.
- AC-3.2: When no `Cargo.toml` exists, `verify-gate.sh` skips the audit step without erroring.

### US-4
- AC-4.1: `/code:audit --stage <n>` for n in 1..7 runs only the named stage.
- AC-4.2: Invalid stage numbers exit non-zero with a usage message listing valid stages.

### US-5
- AC-5.1: `/code:audit --review` runs the seven stages, then invokes the engineering plugin's `code-review` skill against `git diff` against the merge base of the current branch.
- AC-5.2: The combined output (static findings + review prose) is written to the same `.claude/audit-<UTC>.md` report.
- AC-5.3: If the engineering plugin is not installed, `--review` exits non-zero with a hint to install it.

### US-6
- AC-6.1: Running `/code:audit` in a directory with no `Cargo.toml` at any depth exits 0 with a "not a Rust workspace, skipping" message and writes no report.

### US-7
- AC-7.1: Every audit run writes `.claude/audit-<UTC>.md` where `<UTC>` is `YYYYMMDD-HHMMSS` in UTC.
- AC-7.2: Findings are grouped by severity with CRITICAL first, then HIGH, MEDIUM, LOW.
- AC-7.3: Every finding includes a `path:line` citation linking to the exact source location.

### US-8
- AC-8.1: Stage commands in the audit script are derived from parsing the v3.9.0 CI workflow YAML, not hardcoded duplicates.
- AC-8.2: A unit test asserts the audit's stage list matches the CI workflow's stage list by name and command string.

### US-9
- AC-9.1: When `cargo-machete`, `cargo-audit`, or `cargo-deny` is not on PATH, the corresponding stage emits a WARNING and is skipped.
- AC-9.2: A skipped tool is recorded in the report at LOW severity; exit code remains 0 if no other stage fails.

### US-10
- AC-10.1: Running `/code:audit` against `templates/rust/dioxus-fullstack/` exits 0.
- AC-10.2: A CI job runs the audit against the fixture on every PR to code-et.

### US-11
- AC-11.1: A grep for known org-specific tokens (e.g. "visma", "emerging-tech") across the audit command and scripts returns zero hits.
- AC-11.2: The audit reads its target directory from the current working tree, not from any hardcoded path.

### US-12
- AC-12.1: When the audit reports any non-LOW findings, the first line of the report is a one-sentence summary of the single highest-severity finding plus a remediation hint.
- AC-12.2: The terminal output on failure echoes that same one-line summary so it is visible without opening the report.

## Implementation Decisions

**New module: audit command.** A new slash command under the code module, exposing the audit skill. The skill orchestrates the seven stages, owns the report format, and implements `--fast`, `--stage`, and `--review` flags.

**Stage definitions sourced from CI workflow.** The audit module parses the existing GitHub Actions workflow YAML for the v3.9.0 gate. The parser extracts each step's name and shell command. The audit then shells out to those exact commands in order. This keeps CI as the single source of truth and makes drift impossible.

**Report writer.** A small helper that buffers findings from each stage, sorts by severity, and writes the markdown report. Findings are normalised into a common shape: severity, message, path, line, stage. The writer also prepends the highest-severity summary line.

**Hook into verify-gate.** The verify-gate script gets a guarded invocation: if `Cargo.toml` exists at repo root, run `audit --fast`; otherwise skip. No other gate behaviour changes.

**Hook into implement.** The implement command's skill chain inserts the audit skill (with `--fast`) directly after the simplify skill. Failures bubble up the same way other skill failures do.

**Review-mode chaining.** The `--review` flag conditionally invokes the engineering plugin's code-review skill, passing it the git diff against the merge base. Output is captured and appended to the report under a "Review" section.

**Fixture as smoke test.** The bundled Rust fixture from v3.9.0 doubles as the audit's regression suite. A new CI job in the code-et repo runs the audit against the fixture on every PR.

**Portability.** No hardcoded org names or app paths anywhere. All paths derived from `pwd` or `git rev-parse --show-toplevel`. Bun for any TS shims, UV for any Python shims (per global rules).

## Testing Decisions

External-behaviour tests only — exit codes, report contents, and integration-point side effects. Mirror the test style already used by the simplify and verify-gate modules.

- **Stage-list parity test.** Assert the audit's parsed stage list matches the v3.9.0 CI workflow's stage list by name and command string. This guards US-8 against drift.
- **Fixture smoke test.** Run the audit against `templates/rust/dioxus-fullstack/` in CI; assert exit 0 and a report file exists. Mirror the fixture-based tests already used by the v3.9.0 gate validators.
- **Skip-on-non-Rust test.** Run the audit in a temp dir with no `Cargo.toml`; assert exit 0 and the "not a Rust workspace" message.
- **Stage-flag tests.** For each `--stage <n>`, assert only that stage's commands are invoked (e.g. via a trace log or shim) and the others are skipped.
- **Fast-mode test.** Assert `--fast` runs only stages 1 and 2.
- **Review-mode test.** With the engineering plugin stubbed, assert `--review` produces a report containing both a "Static Analysis" section and a "Review" section. Without the plugin, assert non-zero exit and a hint message.
- **Verify-gate integration test.** With and without `Cargo.toml` in the test workspace, assert the verify-gate either invokes or skips the audit accordingly.
- **Implement-chain integration test.** Run the implement command's skill chain against a fixture with a known dead-code regression; assert the chain halts at the audit step and the report path appears in the chat output.
- **Missing-tool test.** Stub `cargo-machete` (or `cargo-audit` / `cargo-deny`) as missing on PATH; assert the stage is skipped with a WARNING and other stages still run.
- **Portability grep test.** Grep the audit module for org-specific tokens; assert zero hits.

## Out of Scope

- Auto-fix mode (`--fix`). The audit reports; remediation stays manual or via downstream skills.
- Non-Rust language support. v3.10 ships Rust-only. TypeScript/Python audits are deferred.
- Replacing the v3.9.0 CI gate. The CI gate stays; the audit mirrors it locally.
- Changes to `clippy.toml` thresholds or the layer-deps validator script. Those land in their own future PRs.
- Persistent audit history beyond the timestamped reports already written to `.claude/`.
- IDE integration (no LSP, no inline annotations).
- Parallelising stages. v3.10 runs them serially to keep output deterministic; parallelisation can come later if measured slow.

## Further Notes

- **CI yaml as single source of truth** is the load-bearing design choice. Every other piece of v3.10 follows from it. If the parser turns out to be brittle, fall back to a generated `stages.json` checked into the repo and regenerated by a CI job — but never duplicate the stage list by hand.
- The audit report timestamp uses UTC to make reports comparable across machines and CI runs.
- The `--review` flag is the bridge to the engineering plugin's review skill. This is the first cross-plugin dependency code-et takes; document the dependency clearly in the README so users know to install the engineering plugin if they want `--review`.
- v3.9.0's plan (`plans/v3.9.0-rust-clean-architecture.md`) already references audit as a v3.10 follow-up — link this PRD from there for traceability.
